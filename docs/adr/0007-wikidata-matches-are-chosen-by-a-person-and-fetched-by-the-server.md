# Wikidata matches are chosen by a person and fetched by the server

Matching a ship name to a Wikidata item is a judgement, and a wrong automatic match would put false facts on a record, so it is two steps and never automatic. `GET /ships/{id}/wikidata-candidates` lists items for the ship's current name (or a name staff type), searched in Swedish and English and merged, and stores nothing. `PUT /ships/{id}/wikidata/{Q-id}` stores the one a person chose. A real search for "Vasa" returns a city, a journal and a noble family before the ship, so the list is for people, not for picking the first hit.

The PUT takes no body. catalog-api fetches the item from Wikidata itself and stores that, so the label and description are what Wikidata said, the retrieval time is when the server asked, and a caller cannot put its own text on a record under Wikidata's name. The reference is one entry in `subject.external_refs` (a JSONB list that existed since the first migration and is shared by every Subject): `source`, `id`, `label`, `description`, `url`, `retrieved_at` and `chosen_by`. A Ship may hold several matches, because the spec stores external facts as a list; choosing the same item again refreshes its entry instead of adding a copy, and `DELETE` removes one, which needs no call to Wikidata so a wrong match can be undone during an outage. The indexing view and the public Ship page carry the reference without `chosen_by`; it is shown, not searched. A Document's `external_refs` column is not used yet.

Choosing and removing read the list, change it and write it back, so they lock the Ship's row first and two people choosing at once both keep their choice. The Wikidata call happens outside any database transaction (the Ship is checked in a short one before and locked in another after), because a slow Wikidata must not tie up the connections the rest of the archive uses. An item that Wikidata has merged into another is answered under its new identifier, and that is what is stored; this follows Wikidata's documented behaviour and was not seen against the live service.

Wikidata is another organisation's service, so every call is bounded. Each try has a timeout, a failure that may pass (timeout, no connection, 429, any 5xx) is tried again after a doubling pause, anything that would not change (another status, a body that is not what Wikidata sends, an `error` object) is not, and one operation, which can be two searches, never exceeds a total budget however the tries add up: the last try is cut short to fit, and when there is no time left for the pause before another try it stops instead of trying at once. The defaults are 4 seconds, 3 tries, 0.5 seconds of pause and 10 seconds in total. Failures become a 504 (too slow) or a 502 with a sentence written for staff, only for that request; editing, relations, uploads and search do not depend on Wikidata at all. `make resilience` proves it by pointing catalog-api at an address where nothing listens and editing the ship anyway. Requests send a User-Agent naming the project and its repository, which Wikimedia asks of every client. Because staff can only reach this through catalog-api, a scripted client cannot use it to hammer Wikidata unauthenticated.

Tests use a fake Wikidata at its HTTP boundary (`tests/fake_wikidata.py`) that answers like the real API and can be scripted to be slow, return statuses or send broken bodies; the browser test and the smoke script use the real Wikidata and say when the machine cannot reach it (skipped visibly, never passed silently). Rejected: a fake Wikidata deployed in the cluster, because the one external REST API of the project should be shown working for real; searching Wikidata for every ship on upload, which is automatic matching by another name.
