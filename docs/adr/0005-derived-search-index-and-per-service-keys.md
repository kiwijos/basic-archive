# The search index is derived, and each service holds a key of its own

Meilisearch holds nothing catalog-api does not: the indexer fetches each record's indexing view (`/api/catalog/index/...`, a service token for the indexer only, shaped by `contracts/index.view.schema.json`) and never trusts the event, so events can repeat or arrive out of order and `POST /reindex` can rebuild both indexes from empty. A Document is indexed with the facts of the Ships it is linked to (type, builder, place, all their Names), and catalog-api announces a Document again when one of its Ships, or the builder of one, changes, so a rename or a new Relation reaches search without anyone reindexing. Builder and year come from `built_by` Relations, falling back to the launch date. Putting facets only on Ships was rejected: a person browsing Documents would have no way to narrow by the ship they show.

Meilisearch derives a key from the master key and the key's uid, so `scripts/create-secrets.sh` works out the indexer's key (write the two indexes, nothing else) and search-api's key (search only) without calling Meilisearch, and a Job registers them from `k8s/meilisearch/keys.json`. search-api therefore holds no database credentials and cannot write; the master key reaches only Meilisearch and that Job. The cost is that rotating the master key rotates every service key at once.
