# Security: deny by default, one credential per service, and proofs that run

The slice is judged by whether the claims can be shown, so each rule is enforced by something that fails when it is broken: a static audit of the manifests in CI (`hardening/`), and scripts that try the forbidden thing on the running cluster (`make security-test`). A rule with no such check is not counted as done.

**Networking.** One `default-deny` policy blocks all ingress and egress in the namespace, and each allowed path is a pair of policies (an egress rule on the caller, an ingress rule on the callee, since a connection needs both), generated from one table (`hardening/src/hardening/policies.py`, with a test that the committed file matches) and listed in the README. The CNI on Docker Desktop (kindnet) enforces them; this was checked before relying on it, because on a CNI that does not, every policy would be silently ignored. `scripts/netpol_test.py` opens a connection from every pod that can make one (and from throwaway pods in the Ingress controller's namespace, with and without its labels) to every internal port and compares the result with the paths the ticket agreed, written out by hand rather than derived from the policies; a rogue allow rule made it fail, as it should.

Two places depart from the ticket's list of paths, because the list was wrong or incomplete:

- **The worker also reaches Garage.** It downloads a scan from the presigned address catalog-api signs, which points at Garage. Rejected: streaming scans through catalog-api to remove the path, because large drawings (tens of megapixels) would then pass through one pod's memory and the API's request path. The path is limited to Garage's S3 port.
- **"The internet" for catalog-api means public addresses on port 443.** A NetworkPolicy cannot name Wikidata, whose addresses change, so the rule excludes the private ranges (which hold the cluster and the host) and allows only HTTPS. Naming the host needs an FQDN-aware policy engine such as Cilium; that is the production path.

**A cost seen in testing.** kindnet enforces policies in user space and logs bursts of receive errors; the intermittent five-second stalls and failed tile loads that appeared once policies were applied coincide with them (README, "A limit of this environment"). The cause is not proven. It does not change what the policies allow, only how reliably this particular CNI applies them, and it is the reason the rollout check reports slow answers rather than only failed ones.

**Credentials.** Each service holds only what it uses (`hardening.audit.AUDIENCE` lists who may read each Secret, and the audit fails if a workload reads one that is not its own, or a new Secret has no stated audience). RabbitMQ now has a login per service, created by the broker when it starts from a `rabbitmq-users` Secret: catalog-api may only publish to the events exchange, the worker may read `ocr.requested` and publish the next attempt, and the indexer may only read `record.changed`. The broker's administrator login is used by nothing. The ticket asks for the Meilisearch master key to be held "only by the indexer"; in fact only Meilisearch and the Job that registers keys hold it, and the indexer holds a key derived from it that can write the two indexes and nothing else (ADR 0005), which is stricter. `make credentials-test` tries each credential against what it should and should not do from inside the pod that holds it, and loosening one permission made it fail. **Migrating a cluster.** `create-secrets.sh` moves an existing cluster onto the separate logins: it rewrites the three services' URLs first and creates the `rabbitmq-users` Secret last, so an interrupted run starts again cleanly, and `make deploy` then restarts the broker, which creates the logins. For a moment the services hold a login the broker has not created yet and retry until it exists. This path was taken for real on the cluster that held the 0.11 data, with Postgres and RabbitMQ starting non-root on their existing volumes. **Known gap:** catalog-api still connects to Postgres as the `postgres` superuser. A role limited to the catalog's tables is the fix; it needs the migration Job to own the schema, and was left out to keep this slice to what the ticket asks.

**Containers.** Every container, including Jobs and init containers, runs non-root with all capabilities dropped, no privilege escalation, a read-only root filesystem and the runtime's default seccomp profile, and no pod receives a Kubernetes API token or the `*_SERVICE_HOST` variables that advertise every Service to it. The three third-party stores comply too: Postgres runs as the image's `postgres` user, RabbitMQ as its `rabbitmq` user, and Garage as an unprivileged user. Garage needed two changes: it refuses a secret file that is not mode 0600 and owned by its user, which a Kubernetes Secret volume cannot be, so its two secrets reach it as environment variables; and a volume from before this slice holds root-owned files that the kubelet does not re-own on `hostPath` storage, so one init container runs briefly as root with only `CHOWN`, `DAC_OVERRIDE` and `FOWNER` to hand it over. That container holds the audit's only two exceptions, each with its reason beside it, and an exception nobody needs any more fails the audit, so the list cannot go stale. It can be deleted once every cluster has been redeployed.

**TLS.** The Ingress terminates TLS with a self-signed certificate for `localhost` that `scripts/create-secrets.sh` generates (the private key goes to the cluster on standard input and is never a file in the repository). `make tls-test` checks that the certificate served is the one in the Secret and not the controller's default, that it verifies when trusted, and that TLS 1.1 is refused. Plain HTTP is still served and not redirected: every script on this machine speaks HTTP to `localhost`, the traffic never leaves the machine, and forcing HTTPS would put a certificate flag on all of them. A real deployment would redirect, and would replace the self-signed certificate with one from cert-manager and Let's Encrypt (`docs/security/cloud-tls.md`, documented and not built, as the ticket says).

**Images.** Scanning every image with trivy found 9 critical and 109 high findings in each Python image on first run (16 and 179 in the worker), mostly from a base image a year old. Upgrading Pillow, FastAPI/Starlette and the bases (Debian 13) left no fixable finding in any custom image except Cantaloupe, whose findings sit inside the upstream jar. The images of the init Jobs and the third-party stores are scanned as well: that moved Postgres from 16.4, which carried 7 critical and 82 high findings, to 16.15. Every remaining finding is recorded, grouped by package, with the reason it is accepted, in `docs/security/trivy.md`; the report generator fails if a fixable finding appears elsewhere, and records the Cantaloupe findings accepted today so that a new one fails too. Cantaloupe's are an accepted risk, not a resolved one: they are fixable, but only by a Cantaloupe release, and the HTTP-handling ones (Jetty, Netty) are reachable through the Ingress, so the acceptance rests on containment and the document says so. The worker's acceptance is the weakest, because it parses untrusted files with native libraries; it rests on containment, and the document says so.

**Secrets.** Only templates are committed, and the audit fails if a Secret in `k8s/` holds anything but a `CHANGE_ME` placeholder. `make secrets-scan` goes further: it takes every value of every live Secret in the cluster and searches for each as a literal string in the working tree and in all of git's history. It found none, and found a planted one.
