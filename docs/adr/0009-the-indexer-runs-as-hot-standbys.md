# The indexer runs as hot standbys on a single-active-consumer queue

The ticket asks every self-built service to run at three replicas. The indexer cannot simply do that. It applies each `record.changed` event by fetching the record's current view and upserting it into Meilisearch, and its ordering guarantee is an `asyncio.Lock` inside one process: one change at a time, and none while a reindex runs. Two plain consumers would each hold their own lock, so two events for one record could be applied by two replicas at once, the older view arriving last and overwriting the newer. A test with two indexers and a slow catalog saw two views in flight at the same moment before the change.

So the queue changed, not the indexer's logic. `record.changed` is declared with `x-single-active-consumer: true`: RabbitMQ delivers to one connected consumer at a time and hands over to the next when that one's connection closes, and anything it had not acknowledged is delivered again. Three indexer replicas all stay connected and ready; one works, two wait. When the working one is rolled or killed the next takes over with nothing lost (the event in hand is applied again, which is safe because applying is idempotent), and the in-order guarantee holds across replicas. The tests start two real indexers against a real broker: the most views the catalog ever sees at once is one, and killing the working indexer with `SIGKILL` part-way through twelve events still indexes all twelve.

What this does not give is throughput: the indexer is not a bottleneck here (a change is one fetch and one upsert), and scaling it out would need events partitioned by record, which a single queue does not do. Rejected: leaving the indexer at one replica (the standby makes a rollout and a pod death invisible, which one replica cannot); three active consumers with a lock in Postgres or Meilisearch (a new dependency for a problem the broker already solves); making `apply` compare timestamps (the catalog's view has none to compare, and a stale write would still be possible between the fetch and the upsert).

**A reindex must run in the working replica.** The lock that keeps a reindex from racing changes lives in that process, so a reindex started in a standby could overwrite newer documents with older ones. Each replica registers its consumer under its pod name, `rabbitmqctl list_consumers` marks the active one, and `make reindex` runs there. The standbys' `/reindex` endpoint is still reachable only from inside the cluster, with the token.

**Changing the queue.** RabbitMQ will not change an existing queue's arguments, and importing definitions that disagree fails. The broker's start-up hook therefore deletes `record.changed` once, when it exists without the argument, before importing; whatever it held is repaired by `make reindex` (the index is derived data, ADR 0005). A broker that already has the argument is left alone, and a new one has nothing to delete.
